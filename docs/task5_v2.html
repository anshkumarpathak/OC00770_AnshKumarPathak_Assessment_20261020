Executive summary

AI can take the legwork out of AMS support without taking decisions away from people

The opportunity
  • Routine questions (“why is my invoice blocked?”) take consultant time away from real incidents.
  • SLA breaches are often spotted too late; each one costs service credits and client trust.
  • Risky changes and failed interfaces cause production incidents, late invoices and missing sales data.
What was built

Four AI agents on one shared platform: a support desk assistant for client key users, and agents for SLA escalation, change impact and integration failures. Each reads two enterprise systems, cites every fact, and routes every action to a named approver. A live portal shows all four working, with a monitoring dashboard over every request.

What the evidence shows

QuestionFinding
Is it safe?Yes, by design and in testing. Across 203 test cases, no restricted action took effect; 44 unsafe requests were stopped, including a prompt-injection attempt posing as CFO approval.
Is it accurate?On familiar wording, yes (96–100% on development sets). On wording it was not built for, 40–75% (blind sets). Every miss failed safe: the agent declined instead of guessing.
Is it honest?Answers carry citations to the source record, and an automatic check withholds any fact the systems did not return. Made-up answers: 0% in all sets but one (7% in one blind set).
Does it cope with outages?Yes. When a system fails, it retries, then says plainly that it can't reach the system. This is demonstrated live with a “chaos” control.
Recommendation and decision asked

Switch on the Claude planner (already built behind the same safety layer), starting with the SLA escalation agent, whose only action is a draft a delivery manager approves.

Decision asked: approve a shadow-mode pilot with one client on anonymised tickets, going live only when it beats today's blind scores with zero unsafe actions.

1 · How it works

The AI proposes; a safety layer and a person decide

Every request takes the same path. The AI never has direct access to the enterprise systems: it can only ask, and the safety layer, written in ordinary code, decides what is allowed.

Five controls that make it safe to pilot

1

Propose, never act alone. Every change waits for a named approver.

2

Rules in code, not in the AI. Restricted actions are refused however they are asked for.

3

Cited and checked. Facts must come from the systems, or the answer is withheld.

4

Client data stays separate. Users see only their own company's records.

5

Fully recorded. An audit log of every request, block and decision.

Why this matters for Orane: the safety controls do not depend on which AI model plans the steps. The model can be upgraded, or swapped, without re-approving the safety design, and the same test sets prove nothing got worse.

How to read these numbers

Development sets were used to build the rules, so they are optimistic. Blind sets were written separately by AI reviewers that saw only the data and runbooks, never the code, and were run once: these are the figures to plan on.

The support desk also scored 100% on 14 held-out cases. Response times are for today's offline planner; an AI model adds a few seconds.

One limitation

Today's offline planner only understands wording it was built for. “The 501 change” or “the Meridian store ticket” defeated it. Every miss failed safe, but a user without an answer still waits.

This is the gap the recommended pilot closes: an AI planner understands natural phrasing, and the same safety layer keeps it in bounds.

7 · Recommendation

A staged pilot, starting with SLA escalation

The SLA agent is the safest start: its inputs are structured, its value is easy to measure, and its only action is a draft that a delivery manager approves.

StageWhat happensMove on when
1 · ShadowThe SLA agent runs on one client's anonymised tickets alongside the duty lead. Its drafts are compared with what the team did; nothing is sent.It beats today's blind accuracy, with zero unsafe actions, and duty leads rate the drafts useful.
2 · AssistedDrafts go to the delivery manager for approval and are sent only after approval.Earlier warnings and fewer breaches against the client's baseline.
3 · ExtendAdd the change impact and integration agents for the same client, each in shadow first.Each passes its own blind set and shadow review.
4 · ScaleOffer the support desk assistant to client key users; roll out to further clients.Client sign-off; L1 deflection measured.
What the pilot needs
  • One client willing to take part, and anonymised historical tickets
  • Read-only, least-privilege system accounts in the client's ITSM tool and SAP
  • AI model access, with usage tracked on the dashboard
  • Single sign-on and named approvers
  • An owner for the runbooks the agents cite
Decision asked

Approve a shadow-mode pilot of the SLA escalation agent with one client, with go-live only when it beats today's blind scores with zero unsafe actions.

The agents, safety layer and test sets are built. The pilot adds connections to the client's systems for the shadow stage, and the production safeguards before stage 2.

Technical reference

The four agents share one platform: an AI planner (an offline rule-based planner today; Claude Opus 5.5 is built in but was not run, because no API key was available), a safety layer in code, a system client with validation, retries and duplicate protection, runbook search with citations, a fact check, an approval queue and request tracing. 60 automated tests cover the platform and the portal end to end.

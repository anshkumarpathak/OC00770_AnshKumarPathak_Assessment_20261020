Summary

The four agents (support desk, SLA escalation, change impact, integration failure) share one architecture: a planner proposes tool calls, a guard layer in code decides whether each one may run, and every risky action waits in an approval queue for a named person. Every turn is traced with personal data masked, and a monitoring dashboard shows latency, errors, blocked actions and citations per agent.

The demo portal is live at oc00770-sap-agents.streamlit.app and runs end to end on fictional data.

1 · Architecture

One platform, one guard layer, four agents

Each agent uses exactly two of the six enterprise APIs plus its own runbooks. Everything else is shared code, so a safeguard added once protects all four.

Design principle: safety lives in code, not in the prompt. A confused or manipulated planner, rules or LLM, can ask for something unsafe, but it cannot make it happen: the guard layer refuses tools outside the agent's allowlist, and the APIs only accept changes through approved actions.

2 · One request, end to end

“Escalate all breached tickets”

Step 3 of the SLA walkthrough shows every part of the architecture in one turn: two APIs, a business rule, a citation, an approval and a change that lands only after a person says yes.

  1. Understand. The duty lead's message is classified as an escalation request.
  2. Plan. The planner proposes sla_overview and then draft_escalation.
  3. Guard. Both tools are on the SLA agent's allowlist and their arguments validate. A tool such as change_ticket_priority would be refused here and logged as blocked.
  4. Call the APIs. The API client reads the open tickets from the service desk and the SLA rules from the contracts API. Each response is validated against its schema; a 503 or a timeout is retried up to three times.
  5. Apply the business rule in code. Deadline = opened time + the contract's resolution hours. Only breached or at-risk tickets may be escalated, and only one escalation per ticket can be pending.
  6. Draft, don't send. draft_escalation creates action ACT-0001 in the approval queue, addressed to the AMS delivery manager.
  7. Cite and check. The answer cites [approval:ACT-0001] and the escalation procedure. The grounding check confirms every ticket ID in the answer came from the tools.
  8. Trace. The turn is written to the trace log with its status (pending_approval), latency and tool calls, personal data masked.
  9. Review and approve. The delivery manager may edit the draft, saves the revision, and approves the exact text; the approval is bound to it by a hash and lapses after 5 minutes. With mock writes on, the handler sends the escalation, carrying that text, through the API client with the action ID as its Idempotency-Key, so a retry can't send it twice.
  10. See the effect. ESC-001 appears in the service desk's escalation list in the live view, and the decision lands in the audit log.

Alert thresholds (designed, not wired to a pager): error rate above 5% over 15 minutes, any guard hit, p95 latency above 8 seconds, approvals waiting more than 4 hours. In production these would go to the AMS duty lead's on-call channel.

5 · Resilience, shown live

The chaos slider: failure is part of the demo

Each agent page has an API condition picker for one specific failure per request (error then recovery, unavailable, timeout, malformed data, HTTP 429, HTTP 404) and a Random chaos slider from 0 to 0.8 that makes the agent's two mock APIs fail at random. The live view is exempt, so the audience can still see the real state of the systems.

What this proves

  • No silent failure. A broken or slow system produces an honest “I can't reach it” instead of a confident wrong answer.
  • Retries are visible. Temporary 5xx errors are retried; Monitoring shows the retries and the API errors seen, so a support lead spots a degrading system before users do.
  • Actions stay safe under failure. Changes carry idempotency keys, so a retry after a timeout never applies an unlock, escalation or reprocessing twice.

Automated tests cover the same failure paths: tests/test_api_resilience.py plus a fault-injection section in each agent's test file, and chaos mode in tests/test_portal.py.

6 · Safeguards

Layered defence, built today and planned for go-live

No single safeguard is trusted on its own. Each layer assumes the one before it might fail.

#LayerWhat it stopsStatus
1Tool allowlistEach agent can only call its own tools; anything else is refused before any API is touched.Built
2Denied toolsPayment-block release, bank details, production transports, SAP_ALL, closing or reprioritising tickets, approving changes, resending payment files. Requests for these, including prompt injection, are blocked and logged.Built
3Argument validationMalformed or out-of-range inputs, such as more than 50 messages in one reprocessing request.Built
4Data scopingUsers see only their own company's data; another client's invoice is not shown.Built
5Business rules in codeEscalating an on-track ticket, reprocessing before the vendor exists in SAP, reassessing an approved change, unlocking someone else's user.Built
6Human approvalEvery escalation, CAB submission, reprocessing run and role assignment waits for its named approver, who can revise the draft and approves the exact text (hash-bound, 5-minute expiry; mock writes off by default).Built
7IdempotencyDouble-applied changes after retries.Built
8Grounding checkAnswers containing an ID, date, amount or duration the tools didn't return are replaced with a safe fallback.Built
9Masking and auditE-mail addresses, card and phone numbers are masked in traces; every request, block and decision is in the audit log.Built
10Single sign-on, role-based approversApprovers proven by identity, not chosen from a list as in the demo.Designed
11Least-privilege technical usersEven a bug in the guard layer can't do more in SAP or the ITSM tool than each agent's two or three allowed changes.Designed
12Secrets vaultAPI keys and system credentials never in code or config files.Designed
13Alerts and kill switchThe thresholds in section 4; one switch per agent back to human-only handling.Designed
14Staged rollout and regression testsShadow mode first, then one client, then all; the test sets re-run on every change before release.Designed

Evidence: across all 203 scored test cases, no restricted action took effect, and the guard layers stopped 44 unsafe attempts. Every accuracy miss failed safe.

Development sets were tuned on, so they are optimistic. Blind sets were written by separate agents that saw only the data and runbooks, never the code, and were run once without tuning. Latency is for the offline rules planner; Claude would add model time.

One limitation

The offline planners only understand wording they were built for

Blind accuracy was 40–75%. Phrases like “the 501 change” or “the Meridian store ticket” defeated them. Every miss failed safe, but a user without an answer still waits.

One recommendation

Switch on the Claude planner, starting with the SLA agent

It is built and sits behind the same guard layers. The SLA agent only drafts, so it is the safest start. Pilot in shadow mode with one client, on anonymised real tickets, and go live only when it beats the blind scores with zero unsafe actions.
